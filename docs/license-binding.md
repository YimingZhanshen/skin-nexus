# 正版账号绑定方案（设计文档，不含实现）

> 状态：**方案**。本轮不写实现，只把路线、设计问题与外部前置动作固定下来，供后续独立拍板分段实施。
> 触发条件（任一成立才排期）：① 有站长明确需要「正版玩家进服不被踢」；② 决定支持不挂
> authlib-injector 的原生客户端接入；③ 需要以正版资格作为命名/换肤的优先级依据。
>
> 取证口径：本文引用的竞品事实来自 2026-11-01 的源码快照，逐条出处见
> [`competitor-analysis.md`](competitor-analysis.md) §2.3、§6。概念与公开协议事实的吸收不涉及
> 任何 GPL/AGPL 源码、译文或测试 fixture 的复制与改写（Drasl 为 GPL-3.0、LittleSkin 生态件为
> AGPL/GPL，我方为 AGPL-3.0 但保持独立实现）。

## 1. 术语与现状

- **正版绑定**：把一个本站账号（uid）与一个 Mojang/Microsoft 正版档案（uuid + name）建立可核验的
  对应关系，并在其后允许本站以该档案身份参与认证。
- 现状：本站有**只读的正版兜底**——`profile`/`hasJoined` 本地未命中时向官方 sessionserver 查询，
  开关为 `ygg_mojang_fallback`（`server/internal/ygg/fallback.go`、面板热开关）。它不认证、不绑定、
  不保存任何官方令牌，作用只是「不踢已购买的玩家」。
- 现状：唯一的绑定相关代码是 `server/internal/auth/authsource.go` 的接口占位，**当前无人引用**。
  实施本方案时它应当被真正接线或被删除——留着是「声明但未接线」的技术债。

## 2. 两条路线

| 维度 | 路线 A：官方链路（MS/XBL/XSTS + entitlement 验签） | 路线 B：无状态换肤挑战（Drasl 式） |
|---|---|---|
| 做什么 | 用户走 Microsoft 登录 → XBox Live → XSTS → 查询 Minecraft 所有权（entitlements），把 `pid`（Microsoft 账号 ID）/`uuid`/`name` 与本站 uid 绑定 | 不绑账号：证明「此刻你拥有该正版档案」即可取用其皮肤，例如让原生客户端直接从不挂 agent 的服务器取材质/配置 |
| 依赖 | Entra 应用注册（client id/secret、redirect URI 白名单）、XBL/XSTS 端点、`minecraft-services` entitlements 端点 | `services`/`discovery`/`certificates`/`publickeys` 端点族 + 与 authlib-injector 的兼容口径 |
| 留存什么 | 只留身份映射（uid ↔ pid ↔ uuid ↔ name）与校验时间戳；**绝不保存官方访问令牌/刷新令牌** | 不保存任何东西，或只保存短期挑战态 |
| 撤销 | 解绑即失效（本站侧删除映射）；但**无法撤销微软侧授权**，需另设「重新校验周期」 | 天然无长期态 |
| 失败模式 | 官方端点变更/被墙、外呼合规、微软封应用；重验周期与封禁面交互 | 只解决「取材质/进服」，不解决「谁是正版」；无 agent 客户端生态尚不完整 |
| 我方适配成本 | 高：新增出站依赖、外网可访问回调、账号安全审查、面板灰度 | 中：协议端点族 + 文档；无新外部依赖（除 Mojang 元数据） |
| 判据 | 需要「正版资格」作为业务条件时选它 | 只需要「不挂 agent 也能玩」时选它，两者不互斥 |

**结论**：若只做一件，先做**方案 0**（§4），它把路线 A 的最痛处（绑定后被冒用、进服被踢）用现有能力
压到可接受，且零新外部依赖；路线 A 的完整实现单独分段拍板。路线 B 与「不挂 javaagent 的接入面」同组，
属于协议族建设，不在认证议题里顺手做。

## 3. 七条设计问题（每条都要在实施前落定）

1. **票据生命周期与撤销**：绑定时拿到的 `pid`/`uuid` 是长期身份，令牌是一次性。必须明确：
   是否周期性重验（LittleSkin 生态用 90 天周期重验，出处见 competitor-analysis §2.3）、重验失败后
   是降级为「非正版」还是冻结账号、以及本站能否区分「档案迁移」（正版改名/转移）与「账号丢失」。
2. **与封禁面的交集**：`users.permission=-1` 与材质违规处置都不能被正版身份绕过；反之，正版绑定
   档案是否随封禁一起失效（建议：封禁期不查官方、不返正版材质），避免「被封禁的正版号仍能在进服时
   拿到皮肤」。
3. **`require_verification` 语义冲突**：本站已有邮箱验证门禁（列存在、门禁生效、发信流未实现）。
   正版绑定是**另一种**验证，必须决定：它是否**免除**邮箱验证（建议免除并在面板标注）、以及
   两者都缺失时的优先次序，别把两个 `verified` 混成一个字段。
4. **材质 URL 与 `skinDomains`**：正版档案自带的材质地址来自 `textures.properties`（ Mojang 签名
   过），本站若要代理它需走「改写 URL 的插件 filter」而不是把 mojang 域名塞进 `skin_domains` 白名单，
   后者会让材质代理策略被绕过（该白名单是材质域校验的真源）。
5. **无正版玩家的可玩性**：绑定不能造成「没绑正版 = 二等公民」的可感知退化——默认皮肤、
   本站自传皮肤、命名与进服配额都必须保持原状；正版只用于**优先取官方皮肤**（同名冲突时）等增量。
6. **面板灰度回退**：`auth.microsoft.enabled` 这类开关必须支持「已绑定用户存在时安全关闭」——
   关掉开关后既有绑定映射保留但不再重验、且不影响其进服；给出「先关灰度、再观察、后删码」的三步剧本。
7. **审计与保留期**：绑定/解绑/重验写 `audit_log`，但**不落任何令牌或微软返回的原始 payload**；
   明确保留期与导出（GDPR 视角：`pid` 是第三方个人标识，需在导出面出现），以及删除账号时的级联
   （LittleSkin 的做法是删用户时级联删绑定，`OnUserDeleting.php:10-17`）。

补一条硬约束：**混合认证与 `enforce-secure-profile` 不兼容**。正版客户端若强制 profile key 签名，
本站自签档案必须也能产出可验证的 `publickeys`/`certificates`（我方当前不挂该端点族），否则
「绑定了正版反而进不了服」。这正是路线 B 与路线 A 会互相卡住的地方，必须在设计阶段就判定：
要么整族补齐，要么文档明确「绑定不改变 profile key 行为」。

## 4. 方案 0（零新外部依赖，可先做）

1. 把 `authsource.go` 接线为真实的**多来源认证入口**（本地口令 / 老站 legacy / 未来的 provider），
   或者删除该文件——二者取一，不留空壳。
2. 正版兜底加固：现有 `fallback.go` 已带出站防护与 `ip` 转发。补三件——回源健康检查（探活与
   熔断）、玩家级白名单（仅指定号允许回源命中即放行）、以及回源结果的短 TTL 缓存（避免每次都外呼）。
3. 把「同名冲突时正版优先」的判定做成**离线**能力：管理员手工导入某个正版档案的 uuid/name 到
   本站玩家，保留「导入即留证」的审计（谁、何时、依据什么），不做自动认领。
4. `docs/compat-matrix.md` §4 记一条：正版绑定仍缺，方案 0 不改变这一点（避免文档暗示已支持）。

## 5. 外部前置动作清单（路线 A 必备，任一项未完成即不开工）

| 前置 | 说明 | 归属 |
|---|---|---|
| Entra 应用注册 | 建站方需自有应用（client id/secret、`Authorization Code + PKCE`），重定向 URI 必须是**该站已备案可访问的 HTTPS 地址** | 站长 |
| 域名与 ICP | 回调域名需公网 HTTPS 可解析；中国大陆部署还需备案（见 `docs/deploy.md` 部署前提） | 站长 |
| 微软端点可达性 | `login.microsoftonline.com`、XBL/XSTS、`api.minecraftservices.com` 三处出站；确认部署网络环境允许，并纳入 `internal/outbound` 的受控出站口径 | 我方 |
| 公钥与 profile key 分发 | 若启用 `enforce-secure-profile`，需 `publickeys` + `certificates` 端点族与密钥保管策略（见 §3 硬约束） | 我方 |
| 隐私与条款 | 面向用户说明「绑定会向微软请求哪些标识、保存在本站的是什么、保留多久」；更新 `SECURITY.md` 的支持范围 | 站长 + 我方 |
| 密钥保管 | client secret 只走 env（进 `config.KnownEnv`），面板不落库、不回显——与 SMTP 口令同一口径 | 我方 |

## 6. 红线（禁止形态）

1. **禁止「凭缓存码按邮箱匹配免密继承旧绑定」**：LittleSkin 历史上出现过按邮箱匹配即免密继承
   正版绑定的形态。邮箱是可被接管且会变动的标识，绝不能作为正版资格的凭据。任何「凭 X 自动继承
   旧绑定」的设计都必须以**用户主动的一次认证**为前提。
2. 禁止保存微软/Mojang 的访问令牌或刷新令牌（哪怕加密）——绑定成立后不需要它们，留着只是把
   泄露面永久化。
3. 禁止把「已绑定正版」当作绕过封禁、绕过材质审核、绕过邀请码门禁的通行证。
4. 禁止用正版绑定做隐式实名收集（额外索取身份信息超出本方案目的）。
5. 禁止在关闭灰度开关时静默删除用户绑定数据；删除必须是显式动作并留审计。
6. 禁止把官方材质地址塞进 `skin_domains` 以「顺手」放行——那是绕过本站代理与审计策略。

## 7. 实施顺序（若将来拍板做）

1. 方案 0 全量（含 §4 第 1 条对 `authsource.go` 的处置）。
2. 路线 B 的端点族（`/publickeys`、`POST /player/certificates`、`/api/profiles/{name}`、
   `/api/services/hosts`、discovery），并逐条回答「谁消费它」——写不出消费者就不挂，
   参照 Drasl 的诚实做法：可以挂载但返回 501，不可以假装实现。
3. 路线 A：先只读校验（不入库、仅在管理员输入 uuid 时核验归属），再单次绑定，最后才考虑周期重验
   与面板灰度。每步都可独立回退。
